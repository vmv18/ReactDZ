# Звіт з Лабораторної роботи №3

## Фрагмент коду: Логіка пошуку та фільтрації

```javascript
  const [searchTerm, setSearchTerm] = useState('');
  const [activeCategory, setActiveCategory] = useState('All');

  const categories = ['All', 'News', 'Updates', 'Tech'];

  // Фільтрація постів за пошуком і категорією
  const filteredPosts = postsData.filter((post) => {
    const matchesSearch = post.content.toLowerCase().includes(searchTerm.toLowerCase()) || 
                          post.author.toLowerCase().includes(searchTerm.toLowerCase());
    const matchesCategory = activeCategory === 'All' || post.category === activeCategory;
    
    return matchesSearch && matchesCategory;
  });
```

### Обробка порожнього результату

Щоб інтерфейс був зручним і зрозумілим (UX), програма повинна реагувати на ситуацію, коли користувач ввів запит, за яким не знайдено жодного поста. У коді це реалізовано за допомогою умовного рендерингу (тернарного оператора) у функції `return` компонента `App`:

```javascript
<div className="posts-list">
  {filteredPosts.length > 0 ? (
    filteredPosts.map((post) => (
      <Post key={post.id} post={post} />
    ))
  ) : (
    <div className="empty-state">
      <p>Нічого не знайдено за вашим запитом.</p>
    </div>
  )}
</div>
```
Ми перевіряємо довжину масиву `filteredPosts`. Якщо довжина більша за нуль — рендеримо компоненти `<Post />`. В іншому випадку — показуємо спеціальний блок `.empty-state` з текстом "Нічого не знайдено...".

## Відповіді на контрольні запитання

### 1. Що таке "підняття стану" і чому воно використовується для SearchBar?
**Підняття стану (Lifting State Up)** — це техніка передачі керування станом від дочірнього компонента (наприклад, `SearchBar`) до його спільного батьківського компонента (наприклад, `App`). 
Для `SearchBar` це потрібно тому, що і сам пошуковий рядок, і список постів (який знаходиться "поруч" з ним в `App`) залежать від одного й того ж пошукового рядка (`searchTerm`). Піднявши стан в `App`, ми передаємо значення `searchTerm` вниз у `SearchBar` разом із функцією оновлення `onSearchChange`, а отримане значення використовуємо в `App` для фільтрації списку перед рендерингом. Тепер обидва компоненти синхронізовані.

### 2. Пояснення асинхронної природи оновлення стану в useState
У React виклик функції-сеттера (наприклад, `setSearchTerm`) не змінює змінну стану миттєво в тих рядках коду, що йдуть одразу після нього. Натомість React **планує (schedules)** оновлення та групує *(batching)* декілька оновлень стану для міркувань оптимізації продуктивності, щоб запобігти зайвим перемалюванням (re-renders). Нове значення стану стане доступним лише при наступному рендері компонента.

### 3. Чому для фільтрації створюється нова змінна filteredPosts замість зміни оригінального масиву?
Ми маємо дотримуватись принципу **незмінності (immutability)**. Якщо ми змінимо (відфільтруємо зі збереженням в ту ж змінну) оригінальний масив `postsData` напряму, ми назавжди втратимо пости, які не підійшли під поточний запит. Коли користувач очистить пошукове поле, нам не буде звідки відновити початковий список. Тому ми завжди тримаємо оригінальне `Джерело істини` недоторканим, обчислюючи `filteredPosts` як похідні дані на льоту кожного разу при зміні стану пошуку або категорії.

### 4. У чому перевага використання керованих компонентів над некерованими при реалізації пошуку?
Керовані компоненти (Controlled Components) — це компоненти, де значення форми контролюється безпосередньо станом React (через атрибути `value` та подію `onChange`), а не внутрішнім станом самого браузера-DOM. 
Головна перевага в тому, що React-стан виступає **"єдиним джерелом істини"**. Це дозволяє:
- Миттєво реагувати на кожне натискання клавіші (наприклад, одразу застосовувати фільтрацію для відображення результатів 'наживо').
- Легко реалізовувати валідацію чи форматування введеного тексту просто під час набору.
- При необхідності очищати поле з інших частин компонента (наприклад, кнопкою "Очистити фільтри"). У некерованому підході довелося б працювати з DOM напряму через `refs`, що ускладнило б код і порушило декларативність React.
